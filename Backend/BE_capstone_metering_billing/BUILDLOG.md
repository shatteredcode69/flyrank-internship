# BUILDLOG.md

Honest account of how this repo was built, per the brief's rule 4 in § 3: "AI-assisted building is
encouraged — and owned." This whole repository was generated by Claude (Anthropic) in a single
session, working directly from the capstone brief and the master prompt. That's disclosed plainly
here rather than presented as if a human wrote it line by line.

## What the AI did

- Designed the schema (`migrations/schema.sql`), the layered module structure, and every file in
  `app/`, `tests/`, `scripts/`, plus this documentation set.
- Chose the specific idempotency implementation pattern (always-INSERT, catch the uniqueness
  violation, read back the winner) over a check-then-insert pattern, specifically to avoid the
  race window a naive "SELECT first" approach has between two concurrent retries.
- Chose micro-cents (not plain cents) as the money unit after reasoning through the fact that
  per-token AI pricing is fractions of a cent — plain cents would round sub-cent per-token rates
  to zero.
- Wrote the pinned pricing table in `app/pricing.py` as illustrative, self-consistent rates
  modeled on the shape of real-world AI provider pricing (cached input cheaper than standard
  input, reasoning billed as output) — these are the project's own simulated numbers, not scraped
  from any specific vendor's live price sheet, and are explicitly version-pinned
  (`PRICING_VERSION`) so a future change is a deliberate, tested act.

## The most important limitation to be upfront about: this could not be run end-to-end here

The environment this repo was built in has **no network access** — `pip install fastapi`,
`docker compose up`, and `pytest` (which needs `pytest` itself installed) could not literally be
executed. This is disclosed prominently at the top of `EVIDENCE.md`, not buried.

To avoid the worse failure mode of presenting untested, hand-waved "evidence," the build instead:

1. Wrote the full FastAPI/SQLAlchemy/Postgres codebase as the real deliverable (what runs under
   `docker compose up` on a machine with normal internet access — which is what the evaluator
   will use).
2. Deliberately split out every piece of business logic that has **zero third-party dependencies**
   (`app/pricing.py`, `app/services/cost_service.py`, `app/services/quota_service.py`, and the
   signature-verification methods on both payment adapters, which use only `hmac`/`hashlib`/`json`
   from the standard library) so that logic specifically *could* be imported and executed with
   nothing but a bare `python3` interpreter.
3. Wrote `scripts/verify_core_logic.py`, which imports those real modules (not copies, not
   reimplementations) and runs 16 real assertions against them, including a `sqlite3`-based
   reproduction of the exact unique-constraint pattern `MeteringService` uses for the parts that
   *do* need SQLAlchemy/a real ORM session and so couldn't be imported directly here. That script
   was actually executed; its output in `EVIDENCE.md` is a real terminal transcript, not authored
   prose.
4. Everything downstream of that boundary — the FastAPI route wiring, the async SQLAlchemy
   session handling, the Docker networking, an actual live Stripe Checkout round-trip — is
   **written but not executed** in this environment. The `pytest` suite in `tests/` is real,
   complete, and should pass under `docker compose exec app pytest`, but that specific command was
   never run here. Anyone reviewing this should treat `tests/` as the authoritative test suite and
   `scripts/verify_core_logic.py`'s output as a secondary, already-executed sanity check on the
   dependency-free core — not the other way around.

If this were a real submission, the very next step before demo day would be running
`docker compose up --build && docker compose exec app pytest -v` on a machine with internet access
and fixing whatever surfaces — most likely candidates: SQLAlchemy 2.0 async syntax edge cases,
FastAPI header-alias behavior for `Idempotency-Key`, and JSON column type differences between
SQLite (used by the test suite) and Postgres (production) for the `response_snapshot`/`payload`
columns.

## Corrections made during the build

- Initially wrote the "current month" usage rollup query using Postgres's `func.date_trunc`
  directly in the SQLAlchemy query. Caught during test-suite design that this would make the test
  suite unable to run against SQLite (which the brief's own "no external services needed for
  tests" spirit calls for) — extracted `app/time_utils.py` to compute month boundaries in Python
  instead, so the exact same query works on both databases. This is the one piece of "wrote it,
  then had to go back and fix it" in this build.
- The Stripe adapter's `verify_and_parse_webhook` was written to implement Stripe's signature
  scheme (`t=...,v1=...`, HMAC-SHA256 over `"{timestamp}.{raw_body}"`) by hand rather than
  delegating to the `stripe` SDK's own verification helper. This was a deliberate choice, not a
  correction: it means the security-critical verification path has no hidden SDK behavior and can
  be unit tested with nothing but `hmac`/`hashlib`, which is exactly what let it be part of the
  sandbox-executed verification above.

## Architectural decisions worth explaining at demo (per § 3: "explain 2-3 lines the evaluator picks")

- **Why INSERT-and-catch instead of SELECT-then-INSERT for idempotency** — see `metering_service.py`
  module docstring. The short version: SELECT-then-INSERT has a window where two concurrent
  retries can both pass the SELECT check before either INSERTs, producing two rows. Always
  attempting the INSERT and letting the database's own unique constraint be the arbiter closes
  that window because the constraint check and the write happen atomically in the database.
- **Why 402 is scoped to subscription status, not quota volume** — see `quota_service.py` module
  docstring. A Free tenant who's used their allowance has a perfectly valid, paid-for (i.e. $0)
  plan; they're rate-limited, which is 429. 402 is reserved for "your payment method / subscription
  itself has a problem," which is a categorically different failure a client should handle
  differently (retry-after vs. redirect-to-billing).
- **Why reasoning tokens fold into the output bucket instead of getting their own price constant**
  — see `pricing.py` and `cost_service.py`. This mirrors the brief's stated rule directly and is
  enforced by `test_reasoning_tokens_billed_at_output_rate_not_separately`, which would fail if
  someone added a separate `reasoning_micro_cents_per_token` constant that drifted from the output
  rate.
